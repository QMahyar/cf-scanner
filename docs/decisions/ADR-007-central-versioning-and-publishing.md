# ADR-007: Central versioning control and cargo-dist publishing pipeline

## Status
Accepted

## Date
2026-08-13

## Context
The project reached its first release (v0.1.0) and needs a repeatable way to
version, build, and publish that future developers and agents can follow
without reconstructing the process. Requirements: one place to read the
current version from; no drift between tag, `Cargo.toml`, changelog, and
artifacts; and a publish path that cannot be half-executed by hand. The
v0.1.0 release also exposed the fragility of hand-maintained naming
(xray asset names drift upstream).

## Decision
- **The annotated git tag `vMAJOR.MINOR.PATCH` is the single version source
  of truth.** SemVer semantics: breaking = MAJOR, additive = MINOR, fix =
  PATCH. `Cargo.toml` must match the tag; cargo-dist derives the announced
  version from the tag.
- **Publishing is tag-push-triggered CI only** (`release.yml`, generated by
  cargo-dist 0.32): plan → 3-target build matrix (each bundle checksum-
  verified xray; macOS dropped per ADR-009) → global checksums → host upload
  → GitHub Release. No manual artifact publishing is ever done.
- **Releases are immutable once announced.** A broken release is fixed by
  moving the tag to a fix commit before it announces, or by cutting a new
  PATCH afterwards — never by editing a published release.
- **Changelog entries are written with the change**; release time only
  renames `[Unreleased]` to `[x.y.z] - date`.
- Local build/test/publish flows are documented in `docs/development.md` and
  `docs/release-process.md` so humans and agents share one process.

## Alternatives Considered

### Version only in Cargo.toml, no tags
- Pros: single file, no tag discipline needed
- Cons: no immutable release point in history; cargo-dist needs a tag to
  announce; easy to drift between what is published and what is on disk
- Rejected

### Manual publishing (build locally, attach to a release by hand)
- Pros: no CI dependency
- Cons: unrepeatable, unverifiable, breaks the 3-target matrix (only the
  host target builds locally), MSI needs WiX — exactly the failure mode
  v0.1.0 avoided by using CI
- Rejected

### Dedicated release branch per version (gitflow-style)
- Pros: stabilization space before release
- Cons: unnecessary for a single-binary local tool; trunk-based `main`
  with tags covers the need with far less bookkeeping
- Rejected

## Consequences
- Anyone can reproduce any release: checkout tag, `dist build`.
- CI failures are the only release failure mode; they are visible in the
  run history and publish nothing (host job requires all builds green).
- Tags must be pushed, not force-rewritten after announcement; `git tag -f`
  is reserved for pre-announcement fixes.
- New maintainers and agents read `docs/development.md` +
  `docs/release-process.md` (referenced from AGENTS.md) instead of
  re-deriving the process.
- Upstream drift (xray asset naming) surfaces as a CI build failure and is
  fixed by pinning, never by silent fallbacks.
