# Release process: versioning and publishing

This document is the single source of truth for how CF-Scanner is versioned,
tagged, and published. Follow it for every release.

Two workflow files matter. `.github/workflows/checks.yml` runs the PR and
main gates. `.github/workflows/release.yml` is generated by cargo-dist 0.32
and carries four hand-added blocks: the `gate` job, the `cross-check` job,
the attestation step, and the `concurrency` guard. A re-pushed tag cancels
the superseded run, so two Release workflows cannot race `gh release create`.
If you re-run `dist init`, plan to re-apply those four blocks by hand.
`dist-workspace.toml` sets `allow-dirty = ["msi", "ci"]` to preserve the
hand-edited `wix/main.wxs` and the hand-hardened workflow file.

## Versioning control

- **Agents: releases are USER-GATED.** Before you change any version string,
  propose the exact version number to the USER and wait for an explicit yes
  for that number. Version strings live in three places: `Cargo.toml`,
  `npm/cf-scanner/package.json`, and `RELEASE_TAG` in `install.js`. The same
  gate applies to creating, pushing, or moving a tag. Never sneak a version
  bump into an unrelated commit. A version change without approval is a
  process violation even when CI would pass.
- **Semantic versioning applies.** MAJOR means a breaking change (an API
  contract or behavior change). MINOR means new backward-compatible
  functionality. PATCH means a backward-compatible fix. Changes to
  `src/api/` are MINOR or MAJOR by definition, so ask first.
- **The git tag is the source of truth**, formatted `v<MAJOR>.<MINOR>.<PATCH>`
  (for example, `v0.1.0`). cargo-dist derives the announced version from the
  tag. The artifact, the tag, and the changelog must agree. The `version`
  field in `Cargo.toml` must match the tag you intend to release.
- **Write changelog entries together with the change**, not at release time.
  `CHANGELOG.md` follows Keep-a-Changelog format, newest on top. At release
  time, rename `## [Unreleased]` to `## [x.y.z] - YYYY-MM-DD` and nothing else.

## Prepare the release

1. **Get USER approval for the version number.** Agents treat this step as a
   mandatory gate: propose the number, then wait for the yes. Humans pick
   the semver bump directly.
2. **Bump the version** in `Cargo.toml`. The git tag is the source of truth;
   the tag, `Cargo.toml`, and the changelog must agree.
3. **Bump the npm wrapper if binaries changed.** Set `version` in
   `npm/cf-scanner/package.json` (a patch bump is enough) and set
   `RELEASE_TAG` in `install.js` to match the tag being released. See
   "npm package" below.
4. **Cut the changelog.** Rename `## [Unreleased]` to
   `## [x.y.z] - YYYY-MM-DD`. Entries were written with their changes, so
   this step moves one header and adds no text. Do not add new
   `[Unreleased]` entries after the cut.
5. **Run the local gates:** `cargo test`, `cargo clippy --all-targets -- -D
   warnings`, `cargo fmt --check`, `cargo audit`.
6. **Commit the release commit** on `main`. The tag will point at it.

## Pre-flight checklist before tagging

1. `cargo test`: all green.
2. `cargo clippy --all-targets -- -D warnings` passes, and `cargo fmt
   --check` passes.
3. `cargo audit` reports zero vulnerabilities.
4. `git status` is clean, and the release commit contains the changelog cut.
5. Recommended: run the local smoke test `dist build --artifacts=local`
   (see `docs/development.md`), then restore the placeholder afterwards.
6. No secrets appear in the diff (`git diff | grep -i secret`).

## Publishing pipeline

```
prepare release (version bump + changelog cut + local gates)
        │
        ▼
release commit on main → git tag -a vX.Y.Z -m "cf-scanner vX.Y.Z"
git push origin vX.Y.Z          # the only trigger — never "publish" manually
        │
        ▼
GitHub Actions "Release" workflow (release.yml)
gate        → the release workflow's own job: test + clippy + fmt + audit
                (--locked) on the exact tagged commit (fail = no artifacts;
                a leaner subset than checks.yml — no build/doc-tests/
                coverage/placeholder guard)
  cross-check → cargo check --all-features on every release target (PRs + main/tags; ensures dist-bundle-xray is visible outside PRs)
  plan        → resolves the 3-target matrix + manifest
  build-local → per target: dist build (bundles checksum-verified xray),
                archives + .sha256 + MSI (windows runner ships WiX)
  build-global→ aggregate sha256.sum, source tarball
  host        → artifact attestations, then uploads artifacts to the GitHub
                Release (vX.Y.Z)
  announce    → release notes from the changelog
  npm-publish → after host: publishes `@qmahyar/cf-scanner` from
                `npm/cf-scanner/` (wrapper downloads the binary from the
                just-created Release; requires the `NPM_TOKEN` secret)
```

Pushes to `main` and every PR trigger the `Checks` workflow. It runs test +
clippy + fmt (unconditionally; CRLF is normalized via `.gitattributes`) and
`cargo check --all-features` (so `dist-bundle-xray` is visible on `main`, not
only on PRs) on `ubuntu-latest`, `windows-latest`, and `macos-latest`.
`Checks` also runs doc tests, coverage (`--all-targets --doc`; doc tests are
included in the llvm-cov gate), `cargo audit`, the xray-parity job (which
fails fast if the pinned XTLS release disappears), and the placeholder guard.
Tag pushes and PRs additionally run the Release workflow in plan mode.

## First-time npm setup (one time)

The first publish creates the package; there is no claim step.
`@qmahyar/cf-scanner` was first published on 2026-08-17 at 0.4.0, and later
publishes update it in place. Three things must exist before CI can publish:

1. **Scope ownership.** Only the npm account or org that owns the scope can
   publish a scoped package. `npm whoami` must print `qmahyar` on any
   publishing machine. When it prints E404 or E403 instead, every publish
   fails that way even while logged in. An E401 means nobody is logged in.
2. **Local login** on dev machines, for documented emergencies only: run
   `npm login` inside `npm/cf-scanner/`.
3. **The NPM_TOKEN repository secret.** On npmjs.com, open Access Tokens,
   generate a token of type **Automation**, then run `gh secret set
   NPM_TOKEN`. Without the secret, the Release workflow's `npm-publish` job
   fails at `npm publish` with `ENEEDAUTH need auth`.

### The NPM_TOKEN lifecycle (agent-facing)

- The token is an npm automation token, so it bypasses 2FA and OTP prompts.
  It is stored only in GitHub's encrypted repo secrets. `gh secret list`
  shows it; it never appears in the repo, logs, or artifacts. The current
  one was set on 2026-08-18 and expires after 90 days.
- Every release after a tag push is fully automatic. The `npm-publish` job
  reads `NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}`, publishes
  `@qmahyar/cf-scanner` at the `package.json` version, and no human login
  is ever needed.
- **Expiry signal.** The job fails with `ENEEDAUTH need auth`, or with E401
  or 403 from the registry, even though the secret exists and the
  RELEASE_TAG guard passed. That means the token expired or was revoked.
  Do not debug the workflow. Ask the user for a fresh 90-day automation
  token, run `gh secret set NPM_TOKEN`, then re-run the failed job or
  re-push the tag per the fix flow. Afterwards verify with
  `npm view @qmahyar/cf-scanner version`.

## npm package

`@qmahyar/cf-scanner` lives in `npm/cf-scanner/` and is a thin
binary-download wrapper. Its postinstall fetches `cf-scanner-<target>.<ext>`
(tar.xz on Unix, zip on Windows) from the GitHub Release pinned by
`RELEASE_TAG` in `install.js`. Dist archive names carry no version; only the
release tag selects one.

Publishing is automatic. The Release workflow's `npm-publish` job runs after
`host` creates the GitHub Release, which the install script downloads from.
It requires the `NPM_TOKEN` repository secret described under first-time npm
setup. An automation token is required because it bypasses the interactive
OTP that npm 2FA demands on publish. Nothing runs locally. The only action
happens in the release commit, before tagging:

1. Bump `version` in `npm/cf-scanner/package.json` and set `RELEASE_TAG`
    in `install.js` to the tag about to be pushed. The two MUST match and
    MUST equal `Cargo.toml` `version`: the `version-parity` job enforces
    `Cargo.toml == npm package.json == RELEASE_TAG` (all three). A wrapper
    pointing at the wrong release must not publish.
2. The job verifies alignment: a grep step fails the job unless `RELEASE_TAG`
    equals the released tag, and `version-parity` fails unless all three
    versions match.
3. Smoke-test after the release: run `npm i -g @qmahyar/cf-scanner` on the
   three supported platforms (linux x64/arm64, win32 x64). macOS is
   unsupported for the same reason the release matrix dropped it (ADR-009).

Known npm quirks:

- npm refuses to republish a version that already exists, so always bump. If
  a broken version escaped (for example, 0.4.0 published with the wrong
  filename), unpublish stays blocked for 24 hours, and the last version can
  never be removed. The fix is a PATCH bump, the same as a broken binary
  release.
- Interactive `npm publish` needs a one-time password because of npm 2FA;
  the CI automation token bypasses it. Publish manually only in a documented
  emergency, using an automation token, which is publish-capable too.

## Post-publish verification

1. Run `gh run watch <run-id>` to completion.
2. Run `gh release view vX.Y.Z`. Confirm the 3 platform archives,
   installers, and sha256 files exist, and `isPrerelease` is false.
3. Spot-check one archive: compare its SHA-256 against the published
   `.sha256`, and confirm the real xray binary sits next to `cf-scanner`
   inside, with non-zero size.
4. Verify provenance: `gh attestation verify <artifact> --owner QMahyar`
   succeeds. The `host` job attests every published artifact.
5. Check npm: `npm view @qmahyar/cf-scanner version` shows the bumped
   version, and `npm i -g @qmahyar/cf-scanner` on at least one platform
   downloads and runs. `cf-scanner scan --preset quick --target 20` runs a
   quick scan and prints NDJSON results.

## Fixing a broken release

If CI fails or artifacts come out wrong (for example, the v0.1.0 xray
asset-name failure):

1. Fix on `main` with the normal gates and let `Checks` pass.
2. Move the tag to the fixed commit and re-push it:

   ```
   git tag -f vX.Y.Z            # tag now points at the fix commit
   git push origin :vX.Y.Z      # delete remote tag
   git push origin vX.Y.Z       # re-push → fresh Release run
   ```

3. Verify again per "Post-publish verification". The failed run stays in
   history as-is and publishes nothing, because the `host` job requires all
   builds green. No orphan release can exist.

Only a release that has not been announced can move this way. Once a release
exists, never rewrite it; cut a new PATCH instead.

## Known gotchas

- XTLS asset naming drifts: arm64 takes the `-v8a` suffix, and macOS assets
  say `macos`, not `darwin`. If a build job dies downloading xray, check
  `build.rs::xray_asset` against the real asset list before anything else.
- The gh token needs `workflow` scope to push repos that contain workflow
  files. Refresh it with `gh auth refresh -h github.com -s workflow`.
- The 0-byte `data/bundled/*` placeholders are git-tracked. A local release
  build overwrites one of them during `dist build` and deletes the other
  target's placeholder; later builds recreate it. Restore both before
  committing: `git restore data/bundled/xray data/bundled/xray.exe`. CI is
  unaffected because each job checks out fresh.
- Windows binaries are unsigned, so SmartScreen warns. Accepted.
- Attestation needs `id-token: write`. The `host` job's
  `attest-build-provenance` step requires the OIDC token, so the
  workflow-level `permissions` block must include both `id-token: write` and
  `attestations: write` (both added in the 0.4.0 review cycle). `dist init`
  regenerates that block, so re-check it after any regeneration.
- WiX runs on CI only. MSI builds fail on dev boxes without WiX. Expected.
- The `npm-publish` job needs the `NPM_TOKEN` secret, an npm automation
  token that bypasses 2FA. Without the secret, the job fails at `npm
  publish` with `ENEEDAUTH need auth`; set it with `gh secret set NPM_TOKEN`,
  then re-run the failed job or re-push the tag per the fix flow. The same
  symptom appears after expiry, because the token lasts only 90 days. Ask
  the user for a new one (see "The NPM_TOKEN lifecycle").
- Broken npm versions cannot be removed right away: the last published
  version is unpublishable, and every version locks for 24 hours after
  publish. The fix is a PATCH bump, never a delete, exactly like broken
  binary releases.

## Rollback plan

There is no server deployment to roll back. Users install self-contained
artifacts from a GitHub Release. To roll back, either publish a PATCH that
fixes the broken prior release, or tell users to install the previous
release; previous tags stay downloadable forever. Never delete or edit a
published release.
